# AXIOM LAB production candidate — bundles 13–16

## Included
- 13: Sidebar account panel, current identity, research navigation, storage usage, sign-out. Hosted managed authentication preflight without the legacy shared token. Vercel CSP accepts only the exact configured Supabase origin.
- 14: Optional shared PostgreSQL fixed-minute request quota. Existing process-local global and per-user concurrency caps remain; no distributed concurrency or authenticated response cache is claimed.
- 15: Log summary and bounded health-only probe. Existing request IDs and timing retained. No external telemetry service, no raw user IDs or tokens in the summaries.
- 16: Focused tests and release gate. Optional automatic registration uses verified Google identities, explicit opt-in, cloud storage, distributed quota, and operator blocklist. No manual allowlist needed in open mode. Supabase Auth already persists the identity profile; research is provisioned lazily on first write. No custom profile editor, admin dashboard, or public deployment in this batch.

## Safe installation
Stop frontend/backend. Run installer `--check` and apply. No private environment or data changes. Run frontend typecheck, tests, build and full backend pytest with private settings not exported to the test shell. Preserve the existing beta environment. Run `supabase/axiom_production_setup.sql` in the dedicated AXIOM LAB SQL editor; read it first. It creates a backend-only quota table and two RPCs, no research changes. RLS must be true and anon/authenticated cannot read the table or execute the RPCs. The service role bypasses RLS; server-side tenant checks remain essential.

Keep `AXIOM_OPEN_REGISTRATION=0`. Set `AXIOM_DISTRIBUTED_RPM=1` only after SQL succeeds; restart via scripts/start_backend.py. For the live cloud checks, use `AXIOM_CLOUD_STORAGE=1` with your existing secret key, URL, multi-user and Google settings. Never put the secret key in frontend variables.

## Release gates (record results before opening registration)
- Both invited Google accounts enter automatically, toolbar stays inside sidebar on desktop and mobile, collapsed navigation and sign-out work.
- Each uploads a different synthetic CSV and creates an experiment. Switch accounts and confirm only own history. Direct GETs of other user's dataset/profile, experiment/runs/report and write attempts must return 404 or deny, not expose data. Test missing/invalid token (401), uninvited account (403), and direct Supabase Data API/storage with ordinary auth (denied). Use DevTools network inspection locally; never send tokens or screenshots of keys. Use synthetic data only.
- Verify cloud mode by inspecting the two owners' records in Supabase and checking private object paths. Restart backend and confirm experiment history persists. Run the batch 09–12 backup/restore procedure against disposable data before migration.
- Enable distributed limits and verify the quota table increments for each owner. Test limit in a disposable environment with a low rate and confirm HTTP 429; restore normal rate. Fixed-minute boundaries can permit bursts; keep ingress rate limits and process-local caps.
- Confirm browser console has no CSP or CORS violations. Run `python scripts/configure_vercel.py https://YOUR-ACTUAL-BACKEND --supabase-origin https://YOUR-PROJECT.supabase.co` only after choosing the real backend. Existing generated vercel.json is not overwritten; review and update its exact connect-src manually if already generated. Docker Compose managed-auth frontend build args and Nginx CSP are NOT configured in this batch; use Vite locally and Vercel for hosted preview.
- Hosting: backend uses existing Dockerfile and app.hosted entry point, one worker/replica initially. Set hosted mode, public mode, exact HTTPS frontend origin and Google/cloud env. Cloud mode removes the local persistent-volume requirement only for research stores; verify all features and backups before scaling. No secret in frontend or proxy config. Set VITE_SUPABASE_URL and VITE_SUPABASE_PUBLISHABLE_KEY on frontend host; update Supabase Site URL and exact redirects plus Google audience/branding. Deploy protected preview first.
- Run `python scripts/axiom_release_probe.py http://127.0.0.1:8898` locally or against your own HTTPS frontend. It sends at most 40 health requests with at most four concurrent requests; health timing is not compute capacity. Use existing scripts/capacity_probe.py in isolated local legacy mode with synthetic data for compute tests. Do not claim thousands of users from these checks. Monitor host CPU, RAM, database usage, error rates and actual scientific workload before adding replicas.
- Use `python scripts/axiom_log_summary.py PATH_TO_PRIVATE_LOG` to summarize existing request logs. External alerting, cost monitoring and distributed compute admission remain operational tasks.

## Open registration
Only after passing the above, set `AXIOM_OPEN_REGISTRATION=1` with `AXIOM_GOOGLE_AUTH=1`, `AXIOM_MULTI_USER=1`, `AXIOM_CLOUD_STORAGE=1`, `AXIOM_DISTRIBUTED_RPM=1`. Restart. Google verified identities with confirmed email may now enter without individual IDs. Restrict Google publishing/consent appropriately. `AXIOM_BLOCKED_USER_IDS` is a comma-separated operator-maintained list, checked before invitations/open admission. It is not an admin UI or session revocation guarantee. Disable open registration immediately to return to invitations, and add abusive IDs to the blocklist. Existing user data remains isolated, no automatic deletion. For public operation add signup abuse controls, retention/privacy/account deletion procedures, platform monitoring and load tests; this is a release candidate, not a production sign-off.
