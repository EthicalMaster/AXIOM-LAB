# Reliability and operations — 17–20

- 17: Lifespan-owned connection reuse for Supabase Auth, RPC, and cloud data. Separate pools and a reject-all cookie jar, per-call headers, no retries or token/identity cache. Each request still validates identity. Upstream metrics report HTTP success and elapsed time, not semantic success; measurements are per process, last 256 samples for p95. Owner-only `/api/v1/auth/ops` never includes raw tokens, URLs, identifiers, or research content. It requires the configured admitted owner even with open registration enabled. The owner can open **Operator diagnostics** in the account panel, using the existing authenticated API client; non-owners never see the button. No manual token handling. There is no external alerting service.
- 18: Pending upload audit and explicit recovery. From project root, run `python scripts/axiom_pending_recovery.py --owner YOUR_UUID` to list at most 100 pending records for an admitted workspace. Then add `--dataset DATASET_ID` to check original bytes against the reserved length and SHA-256. If the result is `verified_pending`, stop **all writers** and use `--dataset DATASET_ID --finalize --writers-stopped` to mark only that row ready. No delete or overwrite. Missing objects and hash mismatches stay pending; investigate and restore from a verified backup. A failed network request is not proof that a write did not occur. No automatic cleanup; quotas continue counting pending reservations. Keep snapshots private.
- 19: Bounded upstream operational metrics plus explicit owner check; use the existing health and log summary probes and backend regression tests. The health route proves liveness only, not readiness of every cloud operation. No performance gain or throughput is claimed until measured.
- 20: Compose forwards managed-auth/cloud settings to the backend and passes only public URL/publishable key to the Vite build. Dockerfile checks public values, adds only the configured Supabase project origin to Nginx CSP and avoids logging raw HTTP request targets in Nginx access logs. Error logs and provider logs still need private retention and review. Existing Vercel config generation is unchanged. Compose remains loopback-only, not a hosted deployment. Build and test actual containers before considering them deployable. Never export a secret key as a frontend build variable.

## Release procedure

1. Stop servers, use installer check then apply; run frontend typecheck/test/build and backend pytest with private settings not exported to the test shell. Verify ignored files with `git check-ignore .env frontend/.env.local`.
2. Restart normally and repeat the two-account synthetic isolation tests in cloud mode, including reports and direct access denial. Test open registration on local only and return to closed registration. Verify backup/restore as documented in `docs/CLOUD_BATCH_09_12.md`.
3. Verify owner diagnostics are 200 for the owner and 403 for an invited non-owner. Monitor `auth`, `rpc` and `cloud` p95 before and after a representative synthetic workload. Do not treat health timing as scientific computation capacity. Run the existing capacity probe in an isolated local legacy environment with synthetic data, not against production.
4. Optional: run `docker compose build` and `docker compose up` then open `http://127.0.0.1:8080`. For Google login from the local container frontend add exact `http://127.0.0.1:8080` to Supabase redirect allowlist (including `?view=studio` as needed) and Google JavaScript origins. Use private local settings and keep registration closed. Stop with `docker compose down` (no `-v`). Do not publish this local Compose setup.
5. Hosted preview requires actual host URLs, private environment configuration, exact OAuth redirects, independent live isolation tests, capacity tests, and external monitoring. This batch does not deploy the application or modify live Supabase.
