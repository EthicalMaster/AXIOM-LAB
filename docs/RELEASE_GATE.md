# Final release gate — restricted single-user deployment

## R01: security
- Run the backend suite and existing frontend suite. Enable GitHub branch protection and require `foundation-checks` and `release-security` jobs; configure GitHub secret scanning/push protection if available. `check_private_files.py` checks tracked filenames only, not embedded secrets or git history.
- CI installs and audits Python packages using pip-audit and the npm lockfile using npm audit. Review findings, remediate, re-test. Scan container images and review base images and third-party code before release. Do not dismiss findings solely because tests pass.
- Test authorization, same-origin browser mutations, session cookie flags, provider failures, request limits and redaction with synthetic data only. The shared access token is for one trusted operator, not multiple accounts. Logout clears a browser cookie; token rotation invalidates all old signed cookies. No individual server-side revocation or tenant isolation. Edge/network abuse protection is still required because process-wide budgets are shared. Do not publish private datasets.

## R02: capacity and recovery
- `python scripts/capacity_probe.py` is a fixed local, in-process workload using 400 synthetic rows, no external target. It records success and all-response latency, p50/p95/p99, status counts and throughput, and checks recovery after backpressure. It is not a user-capacity or hosting benchmark.
- Record CPU/RAM, volume utilization, response status rates, request duration and provider quotas on the chosen host. For a restricted staging rollout, start with one operator, monitor actual usage, and tune admission only after measurements. Never equate four in-flight computations to four simultaneous users. Larger workloads require an approved staging test by the host administrator, isolated workers, durable jobs and shared quotas before public access.
- Stop the app and ALL writers before taking a snapshot. For the default local runtime directory: `python scripts/storage_backup.py backup runtime backups/snapshot-01 --writers-stopped`. Test restoration into a NEW location: `python scripts/storage_backup.py restore-test backups/snapshot-01 backups/restore-01 --writers-stopped`. The script checks SQLite integrity/foreign keys and each recorded original's length and SHA-256, copies the database using SQLite backup and only the recorded original files. It never replaces an existing destination. Verify the restored copy separately and open a saved report. The CLI does not stop processes, encrypt files, create off-site copies or enforce retention. Use host-specific volume snapshots for containers, and keep backups private. Do not copy a live volume using this procedure.

## R03: deploy to a protected preview first
1. Host the backend from `deploy/Dockerfile.backend`, with repository root as build context. The image defaults to hosted preflight and requires `AXIOM_HOSTED_MODE=1`, `AXIOM_PUBLIC_MODE=1`, a unique random access token (at least 32 characters), exact HTTPS frontend origin, and an existing writable absolute `AXIOM_DATA_DIR`. Use a genuinely persistent mounted volume; the launcher cannot prove persistence. Configure `PORT` as required by the host; keep one process and one replica. Set CPU/RAM/disk budgets, an ingress TLS gateway and host-side rate limits. Keep AI secrets in host settings, not the frontend. Local Compose explicitly sets hosted mode off and stays on loopback.
2. In the Vercel project, use `frontend` as Root Directory, Vite framework, `npm ci` install, `npm run build` build, `dist` output. Set a stable HTTPS preview frontend domain and use exactly that value for `AXIOM_PUBLIC_ORIGIN` in the backend. The backend needs an HTTPS origin reachable from Vercel. Do not use this configuration to bypass an existing access gate.
3. Once you know the real backend origin, generate `frontend/vercel.json`: `python scripts/configure_vercel.py https://YOUR-ACTUAL-BACKEND-HOST`. This writes a static same-origin rewrite for `/api/:path*`, security headers and API no-store. Review and commit the generated config; it includes the backend URL, not credentials. Do not use a placeholder as a live destination. See https://vercel.com/docs/routing/rewrites. Local Vite proxy remains unchanged.
4. Deploy a protected preview, not automatic public production. Confirm valid certificates on both origins, health, access gate, cookie forwarding, exact Origin on browser POSTs, login/logout, import (including permitted file-size boundary), statistics, regression/classification, run history, exports and AI offline fallback. Check network responses for no-store and request IDs. Verify CSP compatibility, mobile layout, keyboard access and reduced motion. No live proxy verification is implied by the local generator test. Verify data survives backend restart; complete an independent backup restore and inspect operational logs.
5. Require passing CI checks, resolved dependency/image findings, reviewed access model, stable measured capacity, alerts (5xx, 429/503 rates, latency, storage, uptime), backups and a tested rollback. Configure Vercel deployment checks/manual approval where supported; do not promote a failed or unreviewed build. Roll back to the last reviewed image and frontend deployment without deleting the data volume. Validate database migration compatibility on a copy first.

## Outstanding release blockers
Actual backend host, Vercel project/domain, TLS, dependency audit results, container build/start, frontend browser tests, independent security review, live performance/monitoring and restore on chosen hosting infrastructure. No public multi-user release is approved by this patch. Public accounts require individual identity, authorization, tenant-scoped storage, distributed quotas and stronger operational controls.
